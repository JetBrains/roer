Generative plugin UI over A2UI, for agent-development scenarios

Plugins today have to ship hand-built React. This looks at replacing that with agent-drafted interfaces — using Google's A2UI protocol as the wire format — and asks, honestly, where TypeSafe's brand-new Jev model does and doesn't belong in that pipeline.

01 Why not just ship a form

The case for generating the interface instead of coding it.

Roer has no plugin system yet — every surface (ChangesView, GoToFile, FileView) is hand-built React shipped in the app itself. A plugin ecosystem changes that math: a plugin author now has to design and ship UI for every shape of input an agent might need — a config form, a multi-step approval, a disambiguation prompt — and maintain it across Roer's own UI changes.

A generated surface flips who authors the pixels. The plugin (or the agent acting on its behalf) describes intent and data — "confirm these three fields before running," "let the user pick one of these five branches" — and a model drafts the actual component tree at the moment it's needed, from a catalog Roer already trusts. The plugin author writes intent once; the interface adapts to the actual data and actual step, instead of a static form built for the worst case.

That only works if the generated tree can't run arbitrary code, and the app doesn't have to guess at a rendering engine per plugin. Both of those are exactly what A2UI was built to provide.

02 What A2UI actually is

Confirmed from Google's spec and blog posts — not a guess.

A2UI ("Agent to UI") is an Apache-2.0, declarative protocol Google published on 2025-12-15, now at stable v0.9.1 with a v1.0 candidate in progress. It solves one specific problem: an agent needs to hand a client a rich interface across a trust boundary, without handing over executable code.

  • Declarative, not code. The agent sends a flat, ID-referenced list of components (Surface, Component, Data Model) as JSON messages — surfaceUpdate, dataModelUpdate, beginRendering. Nothing is eval'd.
  • Client owns the catalog. The agent can only reference component types the client has pre-registered as trusted. Roer would define that catalog — a button, a diff card, a select, whatever it chooses to support — and no plugin or agent can introduce a component outside it.
  • Streams and self-heals. v0.9 added incremental parsing, so a surface can render while the model is still generating it, which matters for a terminal-first app where a blank overlay reads as broken.
  • Transport-agnostic. It rides on A2A or inside AG-UI's CUSTOM events; it's a payload shape, not a network protocol of its own.
  • No Tauri renderer yet. Official renderers exist for Flutter, Lit, Angular and React; Roer would write its own React-side catalog mapped to its existing Darcula styling (lib/theme-darcula.ts) rather than adopt one wholesale.
Why this beats the alternative MCP Apps' ui:// approach renders agent-supplied HTML in a sandboxed iframe — it's a resource fetch. A2UI is "native-first": the client draws its own widgets from data, so a generated surface in Roer can actually look like Roer (same fonts, same Darcula tokens, same overlay behavior) instead of an embedded web page with its own visual language.

03 ADLC scenarios worth building for

Scoped to the lifecycle of developing and configuring an agent or plugin — not general application UI.

Roer's whole premise is a session that outlives any one client (README.md, "Coming to the front"). The moments below are places in that lifecycle where a static form is either wasteful to hand-build or actively wrong for the step, because the step's shape depends on what the agent is doing right now.

First run

Plugin onboarding

A plugin declares what it needs (a token, a repo path, a mode) without shipping a settings screen; the agent drafts the exact form for what's still missing this session.

Approval gate

Plan review before execution

An agent proposes a multi-step change; instead of a wall of text, it renders the plan as a checklist surface the user can edit or approve step-by-step, styled like the existing diff overlay.

Disambiguation

"Which one did you mean"

The agent found three candidate branches, files, or configs; it renders a picker instead of a text list, because the picker is generated per-question rather than templated in advance.

Live state

In-progress task panel

A long-running agent step (tests, a build) reports structured progress the client renders as a live surface — a natural fit for A2UI's incremental dataModelUpdate, alongside the existing terminal.

Mid-session ask

One more input, on demand

The agent hits a fork it can't resolve alone and needs one field back — generated in place, in the overlay pattern App.tsx already uses for Changes, rather than blocking in the terminal as raw text.

Config drift

Re-prompting on schema change

A plugin's expected input shape changes between versions; because the UI is generated from the current schema, there's no stale hand-built form to catch up.

04 Where Jev fits — and where it doesn't

TypeSafe AI announced Jev on 2026-09-15, four days before this draft. Worth taking seriously, worth being precise about.

Jev is not a chat or generation model. It's what TypeSafe calls a "System One" model: it returns typed, calibrated decisions — Choice (pick one of up to 255 options with a probability distribution), Score (a continuous value), and Noul (a calibrated yes/no) — through a non-autoregressive parallel sampler, with no free-text output at all. TypeSafe's own numbers claim 40–200x lower latency and roughly two orders of magnitude lower cost than a frontier LLM on classification-shaped tasks, at comparable accuracy on their published benchmark.

That's exactly the profile that cannot draft an A2UI surface: building a component tree from an open-ended prompt is free-form structured generation, and Jev's whole design point is that it doesn't do free-form generation. So this pipeline needs two models doing two different jobs, not one model doing both.

Job in the pipelineGenerative model (Gemini / Claude / etc.)Jev
Draft the A2UI component tree from plugin intentYes — this is free-form structured generationNo — no free-text/tree output
Pick which cataloged template a request maps to (Choice)Can, but overkillGood fit — bounded option set
Gate whether a drafted surface should render at all (Noul)Can, but slow/costly per gateGood fit — cheap enough to run on every surface update

05 Architecture sketch for Roer

Where this would actually live in the existing codebase.

  1. Plugin declares intent as structured data (schema + current values), not markup — over whatever the plugin transport ends up being.
  2. A generative model drafts the A2UI surface server- or agent-side, scoped to Roer's registered component catalog only.
  3. A new Tauri command carries the message the way pty.rs carries terminal output today — a typed channel into the frontend, not a raw pass-through.
  4. A React catalog/renderer renders it as a new sibling to ChangesView.tsx and FileView.tsx, reusing Darcula tokens (lib/theme-darcula.ts) so a generated surface looks native, not embedded.
  5. It mounts through the existing overlay/tab pattern in App.tsx / lib/tabs.ts — the terminal stays mounted underneath, exactly as Changes and file tabs already require, so a generated surface never risks the session's PTY.
  6. Jev (optional) sits beside step 2, doing template selection and render-gating, called from the same place that requests the draft — not part of the render path itself.

06 Risks and open questions

No Tauri renderer exists Flutter, Lit, Angular and React renderers exist; Roer's React catalog is new work, not an adoption. Budget for building and maintaining it, including keeping it in step with A2UI's still-moving spec (v0.9.1 stable, v1.0 candidate).
The catalog is the whole security model A2UI's safety guarantee is "the agent can only reference what the client trusts." If plugins are ever allowed to extend the catalog themselves, that guarantee weakens to whatever review process governs new catalog entries — worth deciding up front, not after the first plugin asks for a custom component.
Jev is four days old at the time of this draft Announced 2026-09-15 alongside a $40M seed round, from a company that only just left stealth. Its 40–200x speed and hallucination-free claims are TypeSafe's own benchmark numbers, not independently reproduced yet. Treat it as a promising fit for the narrow gating/routing role above, not as infrastructure to depend on for v1.
Streaming UX inside a terminal-first app A2UI's incremental rendering is built for chat-style surfaces. Roer's overlay pattern is deliberate about not disturbing the terminal underneath (README.md, "Local changes"); a generated surface popping in mid-stream needs the same care that the diff overlay already gives to not stealing focus from a running session.

07 Smallest useful prototype

Before building a plugin system, spike the part that's actually unproven: one plugin, one hand-picked ADLC scenario (the approval-gate checklist reads best against Roer's existing diff overlay), one hardcoded catalog of five or six components, no Jev. Ship a generative model drafting real A2UI messages and a minimal React renderer honoring the Darcula tokens. That answers the two questions this document can't: whether a generated surface actually feels native next to the terminal, and how much catalog a real scenario needs before reaching for Jev's routing/gating role is worth the second integration.
